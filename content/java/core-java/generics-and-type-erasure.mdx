<Lead>
Generics are checked by the compiler and then mostly deleted. Every confusing rule follows from
that sentence: invariance, wildcards, unchecked casts, `@SafeVarargs`, and bridge methods. Learn
where the type information lives and the rules stop feeling arbitrary.
</Lead>

## What the compiler buys you

A generic type moves a `ClassCastException` from runtime to compile time.

```java
List raw = new ArrayList();
raw.add("text");
Integer value = (Integer) raw.get(0);   // compiles, throws ClassCastException at runtime

List<String> typed = new ArrayList<>();
typed.add("text");
// typed.add(42);                        // compile error — the whole point
```

The generated bytecode for `typed` still stores `Object`. The safety net is the compiler's type
checker, not the JVM.

## Generics are invariant

`Integer` is a subtype of `Number`. `List<Integer>` is **not** a subtype of `List<Number>`, and that
is correct — a `List<Number>` promises it can accept any `Number`.

```java
List<Integer> ints = List.of(1, 2, 3);
// List<Number> nums = ints;           // compile error
List<? extends Number> nums = ints;    // fine: read-only view of Numbers
```

Arrays are covariant and therefore unsound; generics chose safety over flexibility:

```java
Number[] numbers = new Integer[1];
numbers[0] = 3.14;                     // compiles, ArrayStoreException at runtime
```

<Callout type="java" title="Why arrays are reified and generics are not">
Array stores check the component type at runtime. Generic type arguments are erased, so there is
nothing for a runtime store check to consult. Rejecting covariance is how the language keeps
generic collections type-safe.
</Callout>

## Wildcards: read and write directions

`? extends T` means "some unknown subtype of T". You can read `T` values, but you cannot write —
the compiler does not know the actual type.

`? super T` means "some unknown supertype of T". You can write `T` values, but reading gives only
`Object`.

```java
static double sum(List<? extends Number> values) {
    double total = 0;
    for (Number value : values) total += value.doubleValue();  // read as Number
    // values.add(1);                                            // illegal
    return total;
}

static void fill(List<? super Integer> target) {
    target.add(1);                                             // write Integer
    Object first = target.get(0);                              // read only as Object
}
```

The mnemonic is **PECS**: producer `extends`, consumer `super`.

```java
static <T> void copy(List<? super T> destination, List<? extends T> source) {
    for (T item : source) destination.add(item);
}
```

`List.of()` shows why `super` matters for consumers: its signature is
`static <E> List<E> of(E e1, ...)`, and its type parameter is inferred from the target. A helper
that only accepts `List<T>` can fail where a helper accepting `List<? super T>` succeeds.

## Erasure: what is deleted

| Written | Erased to |
| --- | --- |
| `List<String>` | `List` |
| `T` (unbounded) | `Object` |
| `T extends Number` | `Number` |
| `Map<String, List<Integer>>` | `Map` |
| `T[]` | `Object[]` |

Consequences that show up in code review:

```java
class Box<T> {
    // static T value;              // illegal: T is per-instance, static is per-class
    // T[] items = new T[10];       // illegal: no reified component type
    // if (this instanceof Box<String>) {}  // illegal: not reifiable

    boolean isStringBox(Box<?> other) {
        return other instanceof Box<?>;      // legal, unbounded wildcard
    }
}
```

Overloads that erase to the same signature do not compile:

```java
// void print(List<String> values) {}
// void print(List<Integer> values) {}   // name clash: both are print(List)
```

And two generic types with different arguments are the same runtime class:

```java
System.out.println(new ArrayList<String>().getClass() == new ArrayList<Integer>().getClass()); // true
```

## Bounds and recursive bounds

```java
static <T extends Comparable<? super T>> T max(Collection<? extends T> values) {
    T best = null;
    for (T value : values) {
        if (best == null || value.compareTo(best) > 0) best = value;
    }
    return best;
}
```

`T extends Comparable<? super T>` is the idiom from `Collections.max`. Using
`Comparable<T>` would reject a `Dog` that implements `Comparable<Animal>`, even though that
comparison is perfectly usable. Bounded type parameters are erased to their bound, so a call on
`T extends Number` can invoke `intValue()` without a cast in the source.

## Heap pollution and `@SafeVarargs`

Varargs of a generic type create an array whose component type is erased. The compiler cannot
verify the contents, so it warns.

```java
static <T> List<T> listOf(T... items) {   // warning: possible heap pollution
    return List.of(items);
}

@SafeVarargs                             // promise: this method only reads the array
static <T> List<T> safeListOf(T... items) {
    return List.of(items);
}
```

`@SafeVarargs` is allowed only on `static`, `final` or `private` methods (and constructors) —
methods the compiler knows cannot be overridden with a different, unsafe implementation.

A genuine pollution example:

```java
static void dangerous(List<String>... lists) {
    List<Integer> ints = List.of(1);
    Object[] array = lists;
    array[0] = ints;                     // unchecked, accepted
    String value = lists[0].get(0);      // ClassCastException
}
```

## Raw types are a compatibility hatch

Raw types exist so pre-2004 code still links. Using them today disables checking for the entire
expression:

```java
List<String> names = new ArrayList<>();
List raw = names;
raw.add(42);                             // accepted, no warning at the call site
String name = names.get(1);              // ClassCastException: Integer cannot be cast to String
```

Prefer `List<?>` when the element type is genuinely unknown — it is checked and read-only.

## Type inference is local

`var` and diamond inference work left to right; they do not look at what you do with the variable
later.

```java
var list = new ArrayList<>();            // ArrayList<Object>
List<String> names = new ArrayList<>();  // target type drives inference
var empty = List.of();                   // List<Object>
```

With `var`, add the type witness when it matters: `var names = new ArrayList<String>();`.

<KeyPoints>
- Generics are a compile-time type system over erased runtime types; the JVM sees `Object` and casts.
- Invariance is the price of type safety: arrays chose covariance and pay with `ArrayStoreException`.
- `? extends T` for producers (read), `? super T` for consumers (write) — PECS.
- Erasure blocks `new T[]`, generic `instanceof`, static use of type parameters, and clashing overloads.
- Varargs of a generic type need `@SafeVarargs` plus a genuine guarantee that the array is not written.
- Raw types disable checking; use `List<?>` for genuinely unknown element types.
</KeyPoints>

<InterviewSet>
<Interview question="Why can't you create a generic array, and what do people do instead?" level="mid">
Array creation needs a reified component type, but `T` is erased. `new T[10]` cannot emit the
correct store check, so the language forbids it. Workarounds are `(T[]) new Object[10]` with a
suppressed warning (safe only if the array never escapes), a `List<T>` instead, or an
`Array.newInstance(componentType, n)` call when a real runtime type is available.
</Interview>

<Interview question="Explain PECS with a method signature you have actually used." level="senior">
Producer extends, consumer super. `Collections.copy(List<? super T> dest, List<? extends T> src)`
is the canonical example: the destination consumes `T` values so it accepts any supertype
container; the source produces them so it accepts any subtype container. Reading from a
`? extends T` list gives `T`; writing to a `? super T` list accepts `T` and reads only `Object`.
</Interview>

<Interview question="What is a bridge method and why does it exist?" level="senior">
When a class overrides a method from a generic supertype, erasure changes the supertype signature
(for example `Object get()`), so the override would not match. The compiler emits a synthetic
bridge with the erased signature that casts and delegates to the real method. It is marked
synthetic and `isBridge()`, and reflection code that lists methods must skip it.
</Interview>

<Interview question="Can two methods overload only by generic type argument?" level="junior">
No. Both erase to the same raw signature, so the compiler reports a name clash. The same applies to
overloading on `List<String>` versus `List<Integer>`. Overloads must differ in a way that survives
erasure, such as arity or a non-generic parameter type.
</Interview>

<Interview question="Does `List<?>` allow adding elements?" level="mid">
Only `null`. The compiler cannot know the element type, so no non-null value is guaranteed to be
acceptable. You can read elements as `Object`, check the runtime type, and copy into a new,
properly typed list. `List<?>` is a read-only view for practical purposes.
</Interview>
</InterviewSet>
